# Gerador Automático de Encarte

Aplicação web (Express + XLSX + Puppeteer) que recebe uma planilha Excel `.xlsx` com produtos e gera dois tipos de material a partir da MESMA planilha:
- **Preçários**: PDF de encarte (14 ofertas por página, 2 colunas × 7 linhas) no estilo amarelo de referência.
- **Telas**: conjunto de banners 16:9 em PNG de alta resolução (3840×2160) para TVs/redes sociais, no estilo verde Farmácias Associadas. As telas são montadas **automaticamente** a partir da MESMA planilha e navegadas em **carrossel** (prev/next + "Tela X de N"). **Estrutura fixa**: a **capa** (tela 1) tem **exatamente 2 produtos** empilhados/centralizados verticalmente e lateralizados à direita; da **tela 2 em diante** cada tela tem de **3 a 4 produtos** dispostos conforme a arte de referência (3 = 2 na linha de cima + 1 centralizado embaixo; 4 = grade 2×2). Limites por posição são aplicados no cliente (add/remove) e no servidor (slice). Auto-build: capa = 2 primeiros produtos, resto em grupos de 4. Subir a planilha em QUALQUER aba (Preçários ou Telas) alimenta as telas. Fundo trocável e foto manual por produto. Botões "Baixar esta tela" e "Baixar todas as telas".

- **Cards** (feed): conjunto de posts **1080×1440** (retrato 3:4) para feed de redes sociais, navegados em **carrossel** (prev/next + "Página X de N"), igual às Telas. O fundo decorativo (título, lettering, foto hero, logo) vem de uma **imagem de campanha que o usuário sobe** (um fundo compartilhado por todas as páginas); o app só sobrepõe as partes dinâmicas. **Estrutura fixa**: a **capa** (página 1) tem **exatamente 2 produtos** no canto inferior-direito (empilhados) + bloco de info topo-esquerda (mês+validade, disclaimer, endereço), conforme a arte de referência; da **página 2 em diante** cada página tem de **2 a 4 produtos** centralizados verticalmente (2/3 = pilha centralizada; 4 = zigue-zague escalonado esquerda/direita) + um **rodapé** (régua teal + disclaimer + endereço), sem o bloco de mês/validade. Os cards de produto reutilizam o MESMO estilo das Telas. Na aba só se editam o fundo de campanha, as infos e o nome do arquivo — **as fotos NÃO podem ser removidas** (lista de fotos é só-leitura; decisão do usuário 2026-07). Limites por posição aplicados no cliente (add/remove) e no servidor (slice + validação). Auto-build: capa = 2 primeiros produtos do catálogo, resto em grupos de 4. Botões "Baixar esta página", "Baixar todas (PNG)" e "Baixar todas em PDF".

- **Stories**: conjunto de posts **1080×1920** (retrato 9:16) para stories, navegados em **carrossel** ("Story X de N"), espelho SÓ-LEITURA das Telas como os Cards — mesmos produtos, textos, preços e fotos, mas **REAGRUPADOS**: como uma tela pode ter 4 produtos e um story aceita no máximo 3, o `stories.js` achata todos os produtos das telas e remonta as páginas (capa = 2 primeiros produtos, exatamente; demais páginas em grupos balanceados de 2–3 via `chunkRest`, ex. 4 restantes → 2+2, nunca 3+1). **Estrutura fixa**: capa = bloco info topo (mês/validade+disclaimer+endereço) + 2 produtos empilhados na parte superior-central (o lettering da campanha fica na metade de baixo do fundo); páginas 2+ = 2–3 produtos empilhados centralizados + rodapé (régua teal + disclaimer + endereço). Na aba só se editam o fundo de campanha (arte 1080×1920), as infos (mês/validade/endereço) e o nome do arquivo — **as fotos NÃO podem ser removidas** (lista de fotos é só-leitura; decisão do usuário 2026-07). Botões "Baixar este story", "Baixar todos (PNG)" e "Baixar todos em PDF".

A interface tem uma barra lateral com logo e abas (Preçários | Telas | Cards | Stories).

## Run & Operate

- `pnpm --filter @workspace/api-server run dev` — run the API server (port 5000)
- `pnpm run typecheck` — full typecheck across all packages
- `pnpm run build` — typecheck + build all packages
- `pnpm --filter @workspace/api-spec run codegen` — regenerate API hooks and Zod schemas from the OpenAPI spec
- `pnpm --filter @workspace/db run push` — push DB schema changes (dev only)
- Required env: `DATABASE_URL` — Postgres connection string; `SESSION_SECRET` — segredo da sessão de login.
- Senha de acesso (hardcoded em `src/routes/auth.ts`): `encarteassociadas`.

## Stack

- pnpm workspaces, Node.js 24, TypeScript 5.9
- API: Express 5
- DB: PostgreSQL + Drizzle ORM
- Validation: Zod (`zod/v4`), `drizzle-zod`
- API codegen: Orval (from OpenAPI spec)
- Build: esbuild (CJS bundle)

Cookie `encarte.sid`, 8h. O store em Postgres sobrevive a restart/redeploy — sem ele (MemoryStore padrão) toda reinicialização derrubava as sessões e o cookie existente passava a devolver 401 (sintoma: login ok mas `POST /api/generate` 401).
- Rotas do encarte: `artifacts/api-server/src/routes/encarte.ts` (`POST /api/upload`, `POST /api/generate`, `GET /api/download/:filename`, `GET /api/preview?edit=1`)
- Rotas das telas: `artifacts/api-server/src/routes/telas.ts` (`POST /api/telas/parse`, `POST /api/telas/render` (stateless, devolve HTML p/ `srcdoc`), `POST /api/telas/generate` (1 tela PNG), `POST /api/telas/generate-all` (várias telas PNG, reaproveita 1 navegador via `htmlToPngBatch`, pula telas vazias, numera pelo índice original `<base>_tela_NN.png`), `POST /api/telas/generate-pdf` (PDF único multi-página com todas as telas não-vazias: renderiza os PNGs em alta-res via `htmlToPngBatch` e monta com `pngsToPdf`, 1 tela por página 16:9 paisagem, salva `<base>_telas.pdf`)). Reutiliza `GET /api/download/:filename` (mesmo `output/`). Limites: capa (`isCapa=true`) = `CAPA_MAX_PRODUTOS=2`, demais telas = `TELA_MAX_PRODUTOS=4`, `MAX_TELAS=60`. `sanitizeState(body, forcedIsCapa?)` fatia os produtos pelo máximo da posição; `generate-all`/`generate-pdf` forçam `isCapa` pelo índice (0 = capa).
- Frontend das telas: `artifacts/api-server/public/telas.js` (modelo carrossel: `catalogo[]` + `telas[]` cada `{id, produtos:[...]}`; monta a capa com 2 produtos e as demais em grupos de 4; navega prev/next; editar/adicionar/remover produtos com limites por posição (capa: exatamente 2; telas 2+: 3–4); a disposição é escolhida no template (`telaTemplate.ts`) via classe `layout-capa`/`layout-3`/`layout-4` (fallback `layout-1`/`layout-2`) e o cliente passa `isCapa` em `telaState(tela, isCapa)`; prévia ao vivo via `srcdoc`; baixar 1 ou todas). **Prévia é renderizada NO NAVEGADOR** chamando `window.TelaTemplate.renderTelaHtml(state)` (sem round-trip de rede nem reenvio das fotos/fundo base64 a cada tecla → prévia instantânea, debounce 120ms). Fallback para `POST /api/telas/render` se o bundle do browser não carregar. Guarda de sequência (`previewSeq`) ainda protege o fallback. Catálogo compartilhado com a aba Preçários via `CustomEvent('encarte:catalogo')` + `window.__encarteCatalogo` (disparado em `app.js` após `/api/upload`). **Sincronização ao salvar**: ao salvar edições no Preçário ("Salvar e atualizar PDF"), `app.js` dispara `CustomEvent('encarte:catalogo-update')`; `telas.js` (`syncCatalog` com `{force:true}`) faz **rebuild completo** das telas a partir do catálogo editado (zera `telas` e chama `loadCatalog`). Isso garante que TODAS as edições de preço/descrição apareçam nas telas; em troca, **descarta a organização** por tela (grupos manuais). **As fotos NÃO são mais perdidas no rebuild**: elas vivem num **store compartilhado** `window.__encarteFotos` (mapa `chave → data URI`), então `newItem` as reaplica por chave ao reconstruir. **A chave é composta** `fotoKey(nome, descricao) = trim(nome)+"||"+trim(descricao)` — NÃO só o nome — porque produtos com o MESMO nome mas apresentações diferentes (a apresentação vem no campo `descricao`, ex. "Black 72h" vs "Invisible 72h") são itens distintos e cada apresentação tem a sua própria foto. Usar só o nome fazia todas as apresentações puxarem a mesma imagem. O mesmo `syncCatalog` (sem `force`) atende o `encarte:catalogo` inicial do upload. **Fotos**: aplicar/trocar a foto de um produto (upload ou ao escolher da planilha) chama `publishFoto(nome, descricao, foto)` que atualiza `window.__encarteFotos` (chave composta) e dispara `CustomEvent('encarte:fotos', {detail:{key, foto}})`; o próprio `telas.js` escuta para espelhar a foto por `fotoKey` e o `newItem` reidrata fotos por `fotoKey` no rebuild (fotos sobrevivem ao rebuild). Editar nome/apresentação de um item que já tem foto chama `rekeyFoto(...)` (re-chaveia o store silenciosamente, sem evento, para não perder o foco do campo). **A aba Telas é a fonte da verdade dos Cards**: `pushPreview` chama `publishTelas()`, que serializa o estado completo (`{mes, validade*, endereco, telas:[{produtos:[{nome,descricao,precoInteiro,precoCentavos,foto}]}]}`) em `window.__encarteTelas` + `CustomEvent('encarte:telas')` a cada refresh de prévia, e a aba Cards consome isso (ver linha dos cards). Painel `#panel-telas` em `index.html` (empty-state `#telaEmptyState` + workspace `#telaWorkspace`).

## Architecture decisions

- O servidor api-server original foi estendido em vez de criar um novo artifact: roda em TypeScript/ESM com bundle esbuild, mas o frontend é HTML/CSS/JS estático servido via `express.static`.
- Puppeteer usa o Chromium do sistema (instalado via Nix). O caminho é resolvido em runtime por `which chromium`, com fallback para `PUPPETEER_EXECUTABLE_PATH`.
- O parser do Excel detecta automaticamente a aba que começa com "ENCARTE", localiza o cabeçalho buscando por "Descrição" e "Venda Encarte" (tolerante a colunas vazias entre eles), e usa a coluna seguinte à descrição como descrição complementar.
- O template do PDF usa CSS Grid (2×7) com `@page A4` e divisórias pontilhadas (vertical entre colunas, horizontal entre linhas via `border-bottom` dos cards).

## Gotchas

- O Chromium precisa estar disponível como dependência de sistema (já instalada via Nix). Se faltar, `htmlToPdf` lança erro pedindo `PUPPETEER_EXECUTABLE_PATH`.
- `puppeteer` está na lista `external` do `build.mjs` — não é bundleado. Mantenha-o em `node_modules`.
- `connect-pg-simple` também está na lista `external` do `build.mjs`. Ele lê `table.sql` via `__dirname`; bundleado pelo esbuild, `__dirname` vira `dist/` e o `createTableIfMissing` falha com `ENOENT: dist/table.sql` (a tabela `session` nunca é criada → login não persiste, 401). Externalizá-lo mantém o `require` apontando para `node_modules` onde o `table.sql` existe. O `dev` roda o bundle (`pnpm build` → `dist/index.mjs`), então isso afeta dev E produção.
- Toda a aplicação fica sob o prefixo `/api` (proxy do workspace). A UI é `/api/` e o upload é `POST /api/upload`.
- Cookie de sessão (`encarte.sid`): precisa ser `sameSite: "none"` + `secure: true`. O app roda dentro de um iframe HTTPS (preview/canvas da Replit e app publicado), que é contexto de terceiros; com `lax`/`secure:false` o navegador bloqueia o cookie e todas as rotas protegidas devolvem 401 (sintoma típico: login "ok" 200 mas `POST /api/telas/parse` ou `/api/upload` retorna 401). `trust proxy: 1` faz o express-session respeitar `X-Forwarded-Proto=https`. Para testar via curl use o domínio HTTPS (`$REPLIT_DEV_DOMAIN`), não `localhost` (HTTP não persiste cookie Secure).
